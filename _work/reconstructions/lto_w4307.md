# LTO / whole-program / function-merging audit (w4307)

Status: research note, 2026-11-03. Worktree `wt/w4307`, branch `wave93-w4307`,
base `eea2e3c1`. Scratch is `/dev/shm/w4307`. **No `src/` or build-flag change is
landed**: no candidate strictly improves the gate. This commit contains this note
only. The canonical `cmake-build-match` build was not disturbed; it was only
reconfigured to point `GOF2_ORIGINAL_SO`/`GOF2_FMOD_LIBDIR` at the ground-truth
files for this worktree.

## 0. Bottom line

The original `libgof2hdaa.so` was **not** built with LTO (full or Thin), **not**
with `-fwhole-program-vtables`, **not** with `-fmerge-functions`/MergeFunctions,
and **not** with linker ICF. Every variant is far below the baseline gate and
changes the original's structural fingerprints.

The original carries direct positive evidence of a **non-LTO, per-TU
`-ffunction-sections` object link**:

* **4,524 exported functions**, including 354 template/ctor/dtor bodies that full
  LTO eliminates and 292 that ThinLTO eliminates. The original exports
  `ArraySetLength<T>` (52 B), `ArrayAdd<T>` (36 B), `Array<T>` ctor/dtor instantiations
  and shader `D0` deleting destructors as separate bodies; LTO drops them.
* **`.ARM.exidx` is 3,566 entries / 272 CANTUNWIND / 194 duplicate-address
  groups**, exactly the baseline non-LTO build. Full LTO is 3,177/83/52 and
  ThinLTO 3,421/272/187. The 193 empty-plain-`.text` CANTUNWIND sentinels are
  gold's `fix_exidx_coverage()` signature for one `-ffunction-sections` object
  per TU; LTO does not produce that set.
* **`.rodata` is byte-identical to the non-LTO build (0 differing bytes).**
  Full LTO shrinks `.rodata` by 5,872 bytes and ThinLTO by 320 bytes.
* **The original `.text` is exactly the non-LTO source order**: all 4,524
  exported functions land at their original addresses and 4,161/4,161 adjacent
  address pairs are preserved. The 2,231 dump-mapped functions form 105 TU
  blocks with 104 transitions and 0 interleaving
  (`link_order_tu_reconstruction_w4210.md`). Full LTO preserves only 85.0% of
  adjacent pairs (and loses 354 functions); ThinLTO preserves 3,698/3,699
  adjacent pairs (99.97%) but loses 292 functions and changes sizes.
* **112 groups of raw-identical function bodies sit at distinct addresses**
  (595 functions), e.g. `Ship::getHandling` and `Ship::getHandlingForShop`
  (76 B each at `0x174a68`/`0x174a1c`) and
  `AEMath::MatrixTransformVector`/`AEMath::operator*` (122 B each at
  `0x8073c`/`0x8060e`). ICF folds them; `-fmerge-functions` thunks them.
* **85 four-byte branch thunks**, exactly the baseline count. `-fmerge-functions`
  produces 262 (+177), turning e.g. `ArraySetLength<int>` from 52 B into a 4-byte
  `b.w`.

No variant improves any function's fuzzy percentage (max Δ = +0.0); every changed
function moves down. The remaining 25 non-exact functions are source-shape, not
LTO/merging.

### 3.1 Full LTO

`.text` is **24,932 bytes smaller** (0x12d664 vs 0x1337c8), `.rodata` **5,872
bytes smaller**, `.ARM.exidx` 3,177 entries / 83 CANT / 52 duplicate groups,
`.ARM.extab` 13,400 bytes smaller, `.data`/`.bss` 16 bytes smaller, `.got` 5,052
bytes smaller. The function set drops from 4,524 to 4,170: **354 exported
functions disappear**. They are mostly:

* 131 `Array<T>` ctor/dtor instantiations,
* 31 `ArraySetLength<T>`,
* 30 `ArrayAdd<T>`,
* 16 `ArrayRelease<T>`,
* 3 `ArrayRemove<T>` / 2 `ArrayRemoveAll<T>`,
* 141 others, e.g. `ModStation::OnTouchEnd/OnTouchMove/OnTouchBegin`,
  `AbstractGun::isRocketGun/isBombGun/isMineGun/isAutoTurret`, every shader
  `D0` deleting destructor, `PaintCanvas::DrawMesh/DrawTransform`,
  `ResourceMesh` ctor/dtor.

The original exports all of those as separate bodies. LTO internalizes and
drops the unused weak/template ones. `.text` order is also wrong: only 85.0% of
adjacent address pairs survive (3,074/3,616), and Spearman rank correlation is
0.9998 (the missing/hoisted functions break the per-TU blocks).

Sanity check: `-flto -fno-inline` still drops to 4,170 functions and leaves
`.text` at `0x136304` (+11,068 vs original), `.rodata` at `0x40477` (-5,872);
official verify is 1167 / 2513 / 3000/4170, 354 missing. The symbol-set loss is
LTO internalization, not just inlining.

### 3.2 ThinLTO

ThinLTO is closer in size but still not the original: `.text` is **636 bytes
larger** (0x133a44), `.rodata` **320 bytes smaller**, `.ARM.exidx` 3,421
entries / 272 CANT / 187 duplicate groups, `.ARM.extab` 11,120 bytes smaller,
`.data`/`.bss` 16 bytes smaller, `.got` 4,720 bytes smaller. The function set
drops to 4,232: **292 exported functions disappear** (131 `Array<T>`
ctor/dtor instantiations, 11 `ArraySetLength<T>`, 12 `ArrayAdd<T>`, 6 `ArrayRelease<T>`,
1 `ArrayRemoveAll<T>`, 131 others). The address order is preserved (3,698/3,699
adjacent pairs, 99.97%, Spearman 0.9999), but the symbol set and sizes are not.

### 3.3 `-fwhole-program-vtables`

`-fwhole-program-vtables` requires `-flto` (the driver rejects it otherwise).
On top of full LTO it is **codegen-neutral**: `.text`, `.rodata`, `.data`,
`.got`, `.dynsym` and `.dynstr` are byte-identical to plain full LTO; the `.so`
sha differs only in the build-id. The official verifier summary is identical
(1277 / 2603 / 3098/4170 / 354 missing). On top of ThinLTO it changes `.text`
content (same 0x133a44 size) and `.data`/`.got`, but the official verifier
summary is also identical (1218 / 2705 / 2972/4232 / 292 missing). Since LTO
itself is disproven, whole-program-vtables is disproven too.

### 3.4 `-fmerge-functions` / MergeFunctions

`-fmerge-functions` is a **cc1-only** flag in clang 7.0.2: the driver rejects
`-fmerge-functions` (`unknown argument`), so the test uses
`-Xclang -fmerge-functions`. It changes 287 function sizes and produces **262
four-byte branch thunks** (vs 85 in the original and the baseline). Examples:

```text
ArraySetLength<int>    original 52 B  ->  4 B  b.w <merged body>
ArrayAdd<AbstractGun>  original 36 B  ->  4 B  b.w <merged body>
MiningGame::down       original 18 B  ->  4 B  b.w <merged body>
```

`.text` shrinks by 128 bytes, `.ARM.extab` by 1,464 bytes, `.ARM.exidx` becomes
3,492 entries / 274 CANT / 196 duplicate groups, and `.got` shrinks by 544
bytes. The gate drops to **1316 byte / 4082 linked / 4237 size-exact**; 422
functions change fuzzy, all downward. The original has only 85 four-byte branch
thunks (the normal PLT tail-call set), so it was not built with MergeFunctions.

`-mllvm -mergefunc` and `-mllvm -enable-merge-functions` are **rejected by
clang 7.0.2**:

```text
clang (LLVM option parsing): Unknown command line argument '-mergefunc'.
clang (LLVM option parsing): Unknown command line argument '-enable-merge-functions'.
```

They are `opt`-level pass names, not registered in this clang; they cannot have
been used with the original's clang 7.0.2 driver. `-fvirtual-function-elimination`
is also unknown to clang 7.0.2 (`unknown argument`).

### 3.5 Linker ICF (`--icf=all` / `--icf=safe`)

Both ICF modes keep the 4,524 symbols but fold identical bodies to one address:

| build | unique addresses | alias groups | symbols in alias groups | groups with identical body at >1 address |
|---|---:|---:|---:|---:|
| original | 4,162 | 354 | 716 | 112 (595 functions) |
| baseline | 4,162 | 354 | 716 | 112 (595 functions) |
| ICF all | 3,337 | 493 | 1,680 | 2 (4 functions) |
| ICF safe | 3,505 | 454 | 1,473 | 30 (347 functions) |

The original's distinct-address duplicate bodies are the direct counter-evidence.
For example:

```text
original:  Ship::getHandling          @0x174a68  (76 B)
           Ship::getHandlingForShop   @0x174a1c  (76 B)
ICF all:   both                      @0x171348
ICF safe:  both                      @0x172214
```

ICF all also changes `.text` from 0x1337c8 to 0x12f99c (-15,916 B) and
`.ARM.exidx` to 2,796 entries / 5 CANT / 0 duplicate groups. ICF safe gives
0x130964 (-11,876 B) and 2,868/5/0. `byte_exact` collapses to 1,347 in both
(3,152 functions lose raw-byte equality because their literal-pool/address
operands move); ICF all also loses one `linked_exact`
(`OnCreateApplication` 100.0 -> 99.8). `.rodata`, `.data`, `.bss`, `.got` and
`.ARM.extab` stay exact. The original's `.text` is 15,916 bytes larger than the
ICF-all build and 11,876 bytes larger than the ICF-safe build, so ICF was not
used.

`.ARM.exidx` fingerprint (prel31 decode; CANTUNWIND is second word == 1):

```python
import struct
sec = next(s for s in e.sections if s['name'] == '.ARM.exidx')
cant = 0; addrs = []
for i in range(sec['size'] // 8):
    off = sec['offset'] + i * 8
    w0, w1 = struct.unpack_from('<II', e.data, off)
    v = w0 & 0x7fffffff
    if v & 0x40000000: v -= 0x80000000
    addrs.append(sec['addr'] + i * 8 + v)
    cant += (w1 == 1)
print('entries', sec['size'] // 8, 'CANT', cant,
      'dup groups', sum(1 for a, k in collections.Counter(addrs).items() if k > 1))
```

## 7. What remains

* The original is a **plain per-TU `-ffunction-sections` non-LTO link**: 4,524
  exported functions, `.text`/`.rodata`/`.data`/`.bss`/`.got`/`.ARM.exidx`/
  `.ARM.extab` all exactly the non-LTO build, and the `.text` order is the
  non-LTO source order.
* No LTO/whole-program/merging flag is a missing build flag. The remaining 25
  non-exact functions are source-shape (register allocation, scheduling,
  basic-block order, expression order), consistent with
  `worst_function_flag_sensitivity_w3751.md` and
  `build_flags_matrix_w4207.md`.
* `-fwhole-program-vtables` is a no-op on this codebase even under LTO; it does
  not deserve a place in the canonical flag set.
* `-mllvm -mergefunc`/`-mllvm -enable-merge-functions` are not usable with the
  original's clang 7.0.2 driver; if function merging is ever wanted, the
  reproducible spelling is `-Xclang -fmerge-functions`, and it is a large
  regression.
