# Radar::draw 73.9% / 9908 B — source-shape analysis (w3804)

**Status:** research note, 2026-11-03. Worktree `wt/w3804`, branch `wave88-w3804`,
base `41804126`. No source change landed: every candidate below either changes
`.text` size (regressing `byte_exact`) or is codegen-neutral. This commit
contains this note only.

## TL;DR

* Baseline: **byte_exact 4498/4524, linked_exact 4498/4524, size-exact
  4524/4524**, `.text 0x1337c8`, lint `CLEAN ✓`, drift 0.
* `Radar::draw` is **9908 B / 73.9%** in both binaries. It is size-exact and
  byte-inexact; the diff is **543 non-equal instruction runs** (difflib on the
  normalized stream, ratio 0.7314).
* The call sequence is almost identical — only **16 call-order/call-count
  differences** across 367 calls. The body is not missing code; it is
  **block order + whole-function register allocation**.
* The single clearest source-order divergence is the **enemy `inSight`
  condition**: the original evaluates the `VectorLength(egoPos - targetPos) <
  60000` term *first*, then the crosshair rectangle in x-pair/y-pair order.
  Our source evaluates the rectangle first, interleaved x/y. Fixing only the
  local order matches that block but costs **+16 B** (`9924`) and drops the
  whole-function fuzzy to **71.2%** because the extra live VFP value
  (`s24`/`s26`) and the shifted block placement re-roll the allocator.
* The original has **one** `getAutoPilotTarget`, **one** `getStationEnumIndex`
  and **one** `strb field_0x1a8`; our source has a second `if (!alienOrbit)`
  autopilot block after the planet loop (two calls, two stores). Deleting it
  shrinks the body to **9740 B** and drops fuzzy to **62.3%**, so the duplicate
  is currently compensating for other missing code. Do not delete it alone.

## 2. What the diff actually is

Normalized-instruction difflib over the two 9908 B bodies:

```text
ratio 0.7314   orig 3532 insns   ours 3528 insns
non-equal runs 543 (replace 486, delete 34, insert 23)
```

Call-sequence difflib (367 vs 370 calls) has only 16 non-equal runs. The
largest are the planet auto-pilot block and the `inSight` block. Everything
else is the same calls in a different block order / different registers.

The prologue already differs: original `vpush {d8-d13}`, ours
`vpush {d8-d11}`. The two extra callee-saved VFP registers are `s24`/`s26`,
used by the original only in the enemy `inSight` block (crosshair x/y held
across the `AEMath::operator-` / `VectorLength` calls). Our baseline keeps the
crosshair ints in `s0`/`s2` and converts them *before* the call, so it needs
only `d8-d11`.

## 3. Enemy `inSight`: the clearest source-order divergence

Original (`0x12ef4c` onward):

```text

12ef50 strb  r6,[r8,#115]        ; enemy->field_0x73 = 0
12ef5a vldr  s26,[r0]            ; crosshair x
12ef5e vldr  s24,[r0,#4]         ; crosshair y
12ef64 ldrd  r2,r1,[sp,#108]     ; egoPos, targetPos
12ef68 blx   AEMath::operator-
12ef6e vcvt  s24,s24             ; convert AFTER the call
12ef72 vcvt  s26,s26
12ef76 blx   AEMath::VectorLength

12ef88 bpl   12efc0              ; false
```

Our source (line ~792) is:

```cpp
if (this->screenX > cx - this->field_0x124 && this->screenY > cy - this->field_0x124 &&
    this->screenX < cx + this->field_0x124 && this->screenY < cy + this->field_0x124 &&
    AbyssEngine::AEMath::VectorLength(this->egoPos - this->targetPos) < 60000.0f) {
```

So the original source order is:

```cpp
if (AbyssEngine::AEMath::VectorLength(this->egoPos - this->targetPos) < 60000.0f &&
    this->screenX > cx - this->field_0x124 && this->screenX < cx + this->field_0x124 &&
    this->screenY > cy - this->field_0x124 && this->screenY < cy + this->field_0x124) {
```

Measured variants (all `-Oz`, Radar's 80:1 `-mllvm` weights unchanged):

| source shape | usize | pct | .text |
|---|---:|---:|---|
| baseline (rect first, x/y interleaved, distance last) | 9908 | **73.9** | 0x1337c8 |
| distance first, x/y interleaved | 9924 | 71.2 | 0x1337e8 |
| distance first, x-pair then y-pair | 9924 | 71.2 | 0x1337e8 |
| distance first, nested `if` | 9928 | 64.7 | 0x1337e8 |
| distance first, direct `inSight = ...` | 9928 | 64.7 | 0x1337e8 |
| rect first, x-pair then y-pair | 9936 | 70.7 | 0x1337e8 |

The local block becomes instruction-for-instruction close to the original
(`vldr s26/s24` before the call, `vcvt` after, x-pair then y-pair), but the
allocator spills `locked` to the stack (`ldr r6,[sp,#144]` at `12efb6`) where
the original keeps it in `r5`, and the false block splits into two
(`12efda`/`12efdc`) instead of the original's single `12efc0`. Net +16 B and a
worse global alignment. Not gate-safe.

## 4. The duplicate planet auto-pilot block

Original has exactly one `getAutoPilotTarget` (`0x12e6f4`), one
`getStationEnumIndex` (`0x12e72a`) and one `strb field_0x1a8` (`0x12e1d0`).
The block is reached only from the top `if (alienOrbit) ... else ...`
(`0x12e1b6 beq.w 0x12e6ee`) and returns to the `field_0x1a8` store via
`0x12e746 b 0x12e1bc`. There is no second copy after the planet loop.

Our source has a second `if (!alienOrbit) { ... getAutoPilotTarget() ...
getStationEnumIndex() ... field_0x1a8 = ... }` after the planet loop
(lines ~640), which emits a second copy at `0x12e72c..0x12e77e` plus a second
`strb field_0x1a8` at `0x12ebe8`. Deleting it:

```text
usize 9740   pct 62.3   .text 0x133728
```

So the original's 168 B must come from code our source is missing elsewhere
(most likely the planet-lock / station-lock tails, which are also placed
differently). The duplicate is currently a size/placement crutch: keep it
until the missing planet-block code is reconstructed, then remove it and the
second `field_0x1a8` store together.

## 5. Other block-order observations

* `otherLock` (first computation, `0x12e2fc`): original is a `cbnz` chain to
  the `otherLock = 1` block (`cbnz; cbnz; cmp; beq far`); ours is
  `cbz first, separate b&&c test block`. Rewriting the source as
  `if (a != null || b != null || c != null)` (with `__builtin_expect(...,1)`)
  or as a named `bool allNull` is **codegen-identical** to the current form
  (9908 B, 73.9%). Removing the `__builtin_expect` gives 9904 B / 72.2%.
* The second `otherLock` (`0x12e376`) already matches closely.
* The gas-cloud spark `inSight` block (`0x12f4a0..0x12f4f8`) is already
  instruction-identical modulo addresses.
* The landmark label `DrawString` is merged with a later `DrawString` in ours
  (`0x12e9e0 b 0x12eaf2`) where the original emits a separate call
  (`0x12e9d8..0x12e9e8`). This is a source-shape difference in the landmark
  loop, but it is entangled with the block placement of the whole landmark
  loop (ours is at `0x12e7a8`, original also `0x12e7a8`, but the planet block
  is laid out before it in both).

## 6. Root cause

The remaining 26% is **whole-function register allocation and basic-block
placement**, not a wrong constant, callee, field or missing body. The
allocator's choices are driven by local live ranges: the enemy `locked`
pointer and the crosshair x/y values. The original keeps `locked` in `r5` and
the crosshair in `s24`/`s26`; ours spills `locked` and uses `s0`/`s2`. The
`inSight` reorder is the correct source shape but cannot be landed alone
because it perturbs the allocation and grows `.text`.

Next pass should reconstruct the planet-block tail (the second `field_0x1a8`
store and the planet/station lock placement) so the duplicate auto-pilot block
can be removed at constant size, then re-apply the `inSight` reorder under the
full gate.
