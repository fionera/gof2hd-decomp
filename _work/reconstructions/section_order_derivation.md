# Section-ordering-file derivation: TU-start alignment (w3424)

Status: research note + landed pass (2026-11-01). Worktree `wt/w3424`, branch `wave87-w3424`,
based on master `d00e0030`. Every number below is from a command run against
`../_work/bins/android_2.0.16_libgof2hdaa.so` or from a controlled rebuild of this tree.

## TL;DR

`tools/gen_section_order.py` reproduces the original's **function order** from the original's
`.dynsym` addresses, but a gold `--section-ordering-file` only fixes the *order*, not the
**addresses**: each clang function section is 2-byte aligned, so a TU whose first function is
4-aligned in the original lands 2 bytes early whenever the previous TU ends at 2 mod 4. The
zero-size `.text.tuend.*` marker that `tools/gen_exidx_markers.py` puts at each TU boundary
carries `sh_addralign`, and gold *does* honour it (a zero-size section's alignment shifts the
next section), so the marker is the lever.

Changing the per-object marker alignment from the hand-maintained 7-object list to **align 4
for every object** is a strict improvement:

```
verify: byte 4182 -> 4227 (+45)   linked 4495 (unchanged)   stubs 0  missing 0  extra 0
data:   exact 843 of 843          sodiff extra 0  imports 207
.text   0x1337c8 (exact)          .rodata 0x41b67 @ 0x1c9e10 (exact)
lint CLEAN   drift 0
```

Exported-function addresses: **4275 -> 4337 of 4524 exact**; the first misplacement moves from
`0x175e08` (`Galaxy::Galaxy`) to `0x11b6d2` (`ResourceTexture::ResourceTexture(String,float)`).

## 1. How the ordering file is derived today

`cmake-build-match/section_order.txt` is generated by `tools/gen_section_order.py` from three
inputs:

1. **Exported functions** — `nm -nD --defined-only` on the original gives every `.dynsym`
   function's address; the ordering file lists `.text.<mangled>` in that address order. This is
   the only part with a complete binary witness.
2. **Local (non-exported) functions** — not in the original's `.dynsym`. They are slotted
   after the last *listed* section that precedes them in their own object (or before the first
   one that follows), i.e. the object's own section order is assumed to equal the original's.
3. **TU boundaries** — `tools/gen_exidx_markers.py` renames each object's empty plain `.text`
   to a unique zero-size `.text.tuend.o<NNN>` (and each archive member's to
   `.text.tuend.a<AA>m<MMM>`), so gold's `fix_exidx_coverage()` keeps one `CANTUNWIND`
   `.ARM.exidx` entry per TU instead of collapsing them onto one ordering index.
   `gen_section_order.py` inserts each marker after its owner's last section.

Before this pass the marker alignment was a hand-maintained list of seven objects
(`KIPlayer`, `Explosion`, `ApplicationManager`, `PlayerStation`, `ResourceMaterial`, `Wanted`,
`Matrix`) at align 4, everything else align 1.

## 2. Evidence: the original's TU starts are 4-byte aligned

The original's `.ARM.exidx` (0x6f70 bytes, 3566 entries) is the only map of function starts
that also covers local functions (compact entries merge runs of up to three functions, so it is
not one entry per function). A `CANTUNWIND` entry (`word1 == 1`) is emitted by gold for
every text input section with no exidx companion — with `-ffunction-sections` that is each
object's empty plain `.text`, i.e. the end of a TU.

For each of the 272 `CANTUNWIND` entries, the next exidx entry's target is the next TU's first
function:

| next target mod 4 | count |
|---|---:|
| 0 | 270 |
| 2 | 1 (`0x6dfce`, `FileInterfaceAndroid::~FileInterfaceAndroid`) |
| (last entry, no successor) | 1 |

So **270 of 271 TU starts are 4-aligned**. That is the whole rule.

Reproduce:

```sh
python3 - <<'PY'
import struct, sys
sys.path.insert(0, 'tools/verify')
from elf import Elf32
e = Elf32('../_work/bins/android_2.0.16_libgof2hdaa.so')
s = next(x for x in e.sections if x['name'] == '.ARM.exidx')
d = e.data
def prel31(x):
    x &= 0x7fffffff
    return x - 0x80000000 if x & 0x40000000 else x
ents = []
for off in range(s['offset'], s['offset'] + s['size'], 8):
    w0, w1 = struct.unpack_from('<II', d, off)
    ents.append(((s['addr'] + off - s['offset'] + prel31(w0)) & 0xffffffff, w1))
from collections import Counter
print(Counter(ents[i + 1][0] % 4 for i, (t, w) in enumerate(ents[:-1]) if w == 1))
PY
# -> Counter({0: 270, 2: 1})
```

## 3. Symptom in the unmodified tree

With the seven-object list, 249 of the 4524 exported functions are not at their original
address. The first is `Galaxy::Galaxy` (`0x175e08` in the original, `0x175e06` here — 2 bytes
early), and the error accumulates through the archives to `-36`:

```
$ python3 tools/... # (see §6) exported address deltas, baseline
exact 4275, nonzero 249
0x175e08 .. 0x175e98  delta -2   n 7
0x1869f4 .. 0x186a34  delta -2   n 2
0x186a6c .. 0x18c66c  delta -4   n 50
...
0x18fe40 .. 0x19362c  delta -32  n 48
0x193c18 .. 0x194030  delta -36  n 53
```

The original's exidx at `0x175e06` is a `CANTUNWIND` sentinel and `Galaxy::Galaxy` starts at
`0x175e08` — exactly the TU boundary the align-1 marker fails to reproduce.

## 4. Measured A/B table

All builds: `cmake --preset default`; `cmake --build cmake-build-match --target check -j8`.
"exact addr" = exported functions whose linked address equals the original's `.dynsym` address
(computed from an unstripped scratch link, §6).

| # | marker alignment | byte_exact | linked | .text | exact addr | first misplaced |
|---|---|---:|---:|---:|---:|---|
| 0 | baseline (7 objects = 4, rest 1) | 4182 | 4495 | 0x1337c8 (exact) | 4275 / 4524 | 0x175e08 (-2) |
| A | **all object markers 4**, archives 1 | **4227** | 4495 | 0x1337c8 (exact) | 4337 / 4524 | 0x11b6d2 (+2) |
| B | all object + all archive markers 4 | 3222 | 4495 | 0x1337ec (+36) | 4524 / 4524 | — |
| C | body markers 4, trailing libgcc markers 1 | 3223 | 4495 | 0x1337ec (+36) | 4524 / 4524 | 0x11b6d2 (+2) |

Variant A is the landed change. Variants B/C prove the rule (every exported function lands on
its original address) but are *worse* on the gate because they add 36 bytes to `.text`: our
archive/local code is 36 bytes smaller than the original's, and the baseline's align-1 markers
were accidentally absorbing that deficit. `.text` size dominates `byte_exact` (it shifts
`.ARM.exidx`, `.ARM.extab` and `.rodata`), so A wins.

Variant C (body markers 4, the trailing libgcc sentinels forced back to 1) gives the same
`.text` size and the same address deltas as B (byte 3223 vs 3222), so the 36 bytes are **real
content**, not tail padding. To reproduce B, pass `4` to the archive-member
`rename_empty_text(...)` call in `gen_exidx_markers.py`; for C, additionally patch the markers
listed in `tail` in `gen_section_order.py` back to `sh_addralign=1` (the variant-C code is not
in the tree — only variant A is). The `.text` tail (the unsymbolised
`0x1d70`-byte blob after `__aeabi_idiv0`) is shifted `+36` in B/C, i.e. the surplus sits in a
local function before the blob.

## 5. What is proven, what is still hypothesis

**Proven**

* The original's TU starts are 4-byte aligned in 270/271 witnessed cases (§2).
* gold honours the `sh_addralign` of a zero-size marker: raising the marker before
  `Galaxy.cpp` from 1 to 4 moves `Galaxy::Galaxy` from `0x175e06` to `0x175e08` (its original
  address). A manual `sh_addralign=8` on the `ListItemWindow.cpp` marker moves
  `StarSystem::StarSystem` from `0x133b64` to `0x133b68`, confirming the mechanism directly.
* Variant A is a strict improvement: byte 4182 -> 4227, linked unchanged, `.text`/`.rodata`
  sizes and bases unchanged, lint CLEAN, drift 0, no new imports, no export delta.
* The remaining 187 misplaced exported functions are all in the archive region
  (`0x18c6c8..0x194030`: libzip, libcrypto, libc++abi), 2..36 bytes early; the only app-code
  misplacement is `ResourceTexture::ResourceTexture(String,float)` at `0x11b6d2` (+2), a genuine
  2-mod-4 TU start.
* Variant B/C place all 4524 exported functions at their exact original addresses.

**Hypothesis / open**

* *Why* the original's TU starts are 4-aligned is not established. It is consistent with one
  `.text` per TU (align 4) rather than per-function sections, but the 194 duplicate alias exidx
  entries argue for `-ffunction-sections`. The 1 exception (`0x6dfce`) and the `ResourceTexture`
  +2 are unexplained.
* The 36-byte content surplus in our archive/local code is not localised yet. It is a source
  size difference, not a layout/flag issue: with B/C the whole `.text` tail moves `+36` while
  every exported function is exact. Fixing it would let B/C keep `.text` exact and would likely
  add more than A's +45.
* `.ARM.exidx` **content** is still far from identical: 3557 of 3566 8-byte entries differ
  (CANT count 272 original vs 273 ours) even though the size (0x6f70) and every section
  base/size are exact. The align-4 marker moves each `CANTUNWIND` target to the aligned
  boundary, so the sentinel target differs from the original's unaligned TU end in the 72 cases
  where the TU ends at 2 mod 4. This is an exidx-only delta, not a function-address delta.

## 6. Reproduction

```sh
# baseline gate
cmake --preset default
cmake --build cmake-build-match --target check -j8
#   verify: byte 4182  linked 4495 ... RATCHET PASS

# the landed change (tools/gen_exidx_markers.py): align = 4 for every gof2 object marker
cmake --build cmake-build-match --target check -j8
#   verify: byte 4227  linked 4495 ... GAIN byte_exact 4182 -> 4227

# exported-function address deltas against the original (needs an unstripped scratch link)
#   build the exact gold command from build.ninja with `-o /tmp/ours_unstripped.so`
#   and without the trailing `strip --strip-all`, then:
python3 - <<'PY'
import sys
sys.path.insert(0, 'tools/verify')
from elf import Elf32
O = Elf32('../_work/bins/android_2.0.16_libgof2hdaa.so')
U = Elf32('/tmp/ours_unstripped.so')
ofn, ufn = O.functions(), U.functions()
rows = sorted((f['value'] & ~1, (ufn[n]['value'] & ~1) - (f['value'] & ~1), n)
              for n, f in ofn.items() if n in ufn)
print('exact', sum(1 for _, d, _ in rows if d == 0), 'of', len(rows))
for a, d, n in rows:
    if d:
        print(hex(a), d, n)
PY
```

The unstripped scratch link is the `COMMAND` of the `libgof2hdaa.so` rule in
`cmake-build-match/build.ninja` with `-o .../libgof2hdaa.so` redirected to `/tmp` and the
trailing `arm-linux-androideabi-strip --strip-all` removed.
