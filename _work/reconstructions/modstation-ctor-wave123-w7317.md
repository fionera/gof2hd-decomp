## 2. The two mutually-exclusive constraints (wave-121/122 recap)

* **Far `x` = `pitch`** (semantically faithful) gives the original register roles
  (near yaw dies in `r3`, pitch is preserved in `r4` via `mov r4,r2`) but the BURR
  pre-RA scheduler swaps the two yaw-table `LDRLIT`s, so the literal pool becomes
  `{Pitch, Yaw, YawIPad}` and the whole near block is permuted: **43 B / 8 runs**.
* **Far `x` = `yaw`** (baseline, semantically wrong) keeps the original pool
  (`{Pitch, YawIPad, Yaw}`) and every byte up to `moveq r0,r4`, but keeps `yaw`
  live across the near call (`r4`), producing `ldr.w r4` + `mov r3,r4`: **11 B / 4 runs**.

The scheduler decision is `ScheduleDAGRRList::BUCompareLatency` with
`BUHasStall(SU, Height) = CurCycle < Height`. Measured heights at the pick
(standalone LLVM-7 `llc -debug-only=pre-RA-sched`, `-g0` IR):

| shape | CurCycle | Yaw height | YawIPad height | stall? | picked first |
|---|---:|---:|---:|---|---|
| `far = pitch` | 15 | 13 | 15 | neither (15<15 false) | **YawIPad** |
| `far = yaw`   | 16 | 16 | 18 | YawIPad stalls (16<18) | **Yaw** |

The heights differ by 3 because the live-out value changes (`pitch` vs `yaw`); the
`MOVCC` height is 12 (`far = pitch`) vs 15 (`far = yaw`), and the two `LDRLIT`
heights are `MOVCC + 1` / `MOVCC + 3`.

## 3. New evidence this wave

### 3.1 Exhaustive near-block IR statement-order search (far = pitch)

The near block is 11 SSA statements with three dependency chains
(`ipad -> icmp -> sel`, `pgep -> pbc -> pl`, `ygep -> ybc -> yl -> yf`, plus `pf`).
All **330 valid topological orders** were generated by renumbering the whole
`base.ll` near block and compiled with the real NDK clang 7.0.2
(`-g0 -S -x ir`). Every single one produces the *same* `far = pitch` near block
(ratio 0.75 vs the target): `Pitch, Yaw, YawIPad` literal order, `str.w r8` and
`mov r4,r2` before the yaw load. The BURR scheduler normalises the DAG, so
front-end statement order is not a lever (confirms wave-121 §6.1 and the
wave-122 §2 conclusion).

### 3.2 A variant with the right pool *and* the right register roles

`int pitchBits = *(const volatile int *)&pitchTable[race]; float pitch = ...;
float yaw = yawTable[race];` (pitch forced through a core register, yaw a plain
float load) with the faithful `far = pitch` gives:

```text
ldr r0,[pc]   ; Pitch
ldr r3,[pc]   ; YawIPad
add r0,pc
ldrb.w r1,[sl]
add r3,pc
ldr.w r2,[r0,r8,lsl#2]   ; pitch
cmp r1,#0
ldr r4,[pc]   ; Yaw
mov r0,r3
str r3,[sp,#180]
add r4,pc
str r4,[sp,#176]
it eq
moveq r0,r4
mov r4,r2                ; pitch -> r4 (live-out)
ldr.w r3,[r0,r8,lsl#2]   ; yaw -> r3 (dead)
str.w r8,[sp,#184]
movs r0,#2
movs r1,#0
add.w r8,sp,#256
strd r1,r0,[sp]
add r1,sp,#320
mov r0,r8
blx
```

This is the only source shape found so far that has **both** the original literal
pool (`Pitch, YawIPad, Yaw`) **and** the original register roles (`yaw -> r3`
dead, `pitch -> r4`). It still measures **44 B / 7 runs, 97.8 %** (avg 99.93) because
the schedule differs: the `Yaw` literal is materialised late (after `cmp`), and
`mov r4,r2` is placed right after the `MOVCC` instead of just before the `blx`
(the RA emits `$r4 = COPY $r2` immediately after the yaw load). Adding a
`__atomic_signal_fence(__ATOMIC_SEQ_CST)` before the pitch load nudges it to
**43 B / 7 runs**; no fence position reaches 11 B.

### 3.4 Exhaustive near-load type / select / declaration sweep (this wave)

A second sweep varied every near-load spelling (volatile-int, non-volatile-int,
volatile-float, plain-float, `memcpy`, volatile pointer) for pitch and yaw,
the far `x` (pitch/yaw), the far `y` (fresh expression / same `yaw` / fresh
volatile local / pointer variable), the select formulation
(`iPad ? YawIPad : Yaw`, `!iPad ? Yaw : YawIPad`, `iPad == 0 ? ...`,
`iPad != 0 ? ...`), the declaration order, and the near `y` (variable vs inline
expression). The result is invariant:

* Only the four `volatile-int` near-load shapes stay at the original 1008 B:
  `far = yaw` is 11 B / 4 runs; `far = pitch` is 43 B / 8 runs.
* `pitch volatile-int, yaw plain float/int, far = pitch` is the only shape with
  **both** the correct pool `{Pitch, YawIPad, Yaw}` and the correct register
  roles (`yaw -> r3` dead, `pitch -> r4` via `mov r4,r2`); it is 44 B / 7 runs
  because the `Yaw` LDRLIT is sunk after `cmp` and `mov r4,r2` is hoisted right
  after `MOVCC`.
* Every `far = yaw`/`far = pitch` shape with the far `y` reusing the near `yaw`
  (live-out, no reload) shrinks the function to 968-1000 B, so the far block
  must keep its own fresh `(iPad ? YawIPad : Yaw)[race]` load.
* `memcpy`-based bit reads collapse to `vldr` and measure 667 B / 86 runs.
* Swapping the select polarity or the declaration order does not change the
  `far = pitch` result (still 43 B), and `yaw`-before-`pitch` declaration grows
  the function to 1000 B.

The far block is byte-identical in every one of these variants (it is the same
`MatrixSetRotation(farKey, pitch, freshYaw, ...)`), so the near-block schedule
difference is driven solely by the near-block IR (load volatility), not by the
far block's live-outs.

### 3.5 Direct check with the real NDK clang

The faithful `far = pitch` shape compiled by the real NDK clang 7.0.2 gives
`str.w r8; mov r4,r2; ldr.w r3; ...; mov r0,r8; blx` and the pool
`{Pitch, Yaw, YawIPad}`. The baseline gives `str.w r8; ldr.w r4; ...; mov r3,r4;
mov r0,r8; blx` and the pool `{Pitch, YawIPad, Yaw}`. The target needs
`ldr.w r3; movs r0,#2; str.w r8; ...; mov r0,r8; mov r4,r2; blx` and the pool
`{Pitch, YawIPad, Yaw}` — i.e. the faithful live-out with the baseline heights.

## 4. Conclusion

The ctor is at the same hard local optimum waves 121/122 found. The target needs
three things simultaneously:

1. `.rodata` = `Pitch, YawIPad, Yaw` (already fixed by the source first-reference
   order; `.rodata` is byte-identical);
2. literal pool = `Pitch, YawIPad, Yaw` — produced only when `yaw` is live across
   the near call (`far = yaw`, the semantically-wrong baseline) or by the
   `pitch volatile-int / yaw plain float` shape (§3.2);
3. near block: yaw -> `r3` (dead), pitch -> `r4` (`mov r4,r2` last) — produced only
   when `yaw` is dead (`far = pitch`).

(2) and (3) are mutually exclusive with clang 7.0.2 `-Oz` at source level: the
live-out value that fixes the RA also fixes the BURR heights, and the two shapes
need opposite heights. The remaining 11 bytes are the post-RA placement of
`str.w r8` plus the `ldr.w r4` / `mov r3,r4` shape produced by the live-yaw choice.
The faithful `far = pitch` spelling is semantically cleaner but measures 43-44 B
(97.8-98.6 %), so the baseline is kept.
