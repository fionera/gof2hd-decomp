The changes are order-only, not new data:

* `Globals.cpp` now defines its `.bss` members in the original `nm -D -nS` order

  (`subMenuIndex`, `logoIsShown`, `isInMainMenu`, `inAppPurchaseSupported`,
  `showNewCreditsMenu`, `showBestDeal`).  The last `.bss` member is a 1-byte `char`,
  so the TU's `.bss` input section is `0x747` bytes, not rounded to 4; that is what
  lets every later TU's `.bss` land at its original address.
* `NdkHooks.cpp` now defines its `.bss` in the original order
  (`0x217b20..0x217b58`): the fourteen 4-byte globals first, then the two
  `double[3]` gravity tables.
* The ten `gi_iap_buy_*_pressed` flags moved out of `NdkHooks.cpp` into
  `GOF2HD2012.c` as strong `= 0` definitions.  The original has them at
  `.bss 0x2179b4..0x2179dc`, between `main.c`'s `zipDirectory` and
  `FileInterfaceAndroid`, which is exactly `GOF2HD2012.c`'s link slot (`o005`).
  Strong definitions are required so they are not COMMON and do not float to the
  end of `.bss`.

These are all 6-62 byte wrappers whose only difference was the PLT/veneer slot of a
tail call.  Gold creates a veneer for a cross-TU tail call in the order the callee is
first referenced by the object; the first reference follows the object's function
order.  Restoring the original definition order in each TU restored the veneer order:

* `Item.cpp`: `isInList(int, Array*)` before `isInList(Item*, Array*)`.
* `Ship.cpp`: `addCargo(Item*)` before `addCargo(Array<Item*>*)`.
* `SpriteGun.cpp`: `update(int)` before `setEnemy(Player*)`.
* `ChoiceWindow.cpp`: `update(int)` after `setMiscButton(String const&)` and before
  `draw()`.

`BeamGun::setEnemy` and the three `TouchButton` methods share veneers with those
wrappers; they flipped with the same reorder.  No function body changed.

## 3. `StatusWindow::reInit`: 4491 -> 4492 (+1)

`StatusWindow::reInit` was the last non-`MGame` row.  Its only difference was the
PIC delta for the file-static `g_sw_charDef`:

```
orig  .word 0x000c0344 -> 0x21839c
ours  .word 0x000c0354 -> 0x2183ac
```

The original `.bss` gap between `StarSystem::orbitPlanetIndex` (`0x218384`) and
`Mission::empty` (`0x2183b0`) is `0x28` bytes:

| range | content |
|---|---|
| `0x218388..0x21839c` | `Radio.cpp` `CHAR_BRENT[5]` (`0x14`) |
| `0x21839c..0x2183a0` | `StatusWindow.cpp` `g_sw_charDef` (`0x4`) |
| `0x2183a0..0x2183b0` | `0x10` bytes, no exported symbol witness |

Our old layout put `LevelScript.cpp`'s `s_processPad[4]` (`0x10`) first, then
`CHAR_BRENT`, then `g_sw_charDef`, so `g_sw_charDef` landed at `0x2183ac`.  The
`s_processPad` array is a reconstruction layout anchor (the original
`LevelScript.cpp` symbol dump has no data symbols), so it was moved from
`LevelScript.cpp` to `TargetFollowCamera.cpp`, the TU linked immediately after
`StatusWindow` (`o159`).  It is declared with hidden visibility so it adds no dynsym
export:

```cpp
// TargetFollowCamera.cpp
#pragma GCC visibility push(hidden)
volatile int s_processPad[4];
#pragma GCC visibility pop
```

```cpp
// LevelScript.cpp
#pragma GCC visibility push(hidden)
extern volatile int s_processPad[4];
#pragma GCC visibility pop
```

The new `.bss` layout is exactly the original:

```
0x218388 Radio.cpp        CHAR_BRENT        0x14
0x21839c StatusWindow.cpp g_sw_charDef      0x04
0x2183a0 TargetFollowCamera.cpp s_processPad 0x10
0x2183b0 Mission.cpp      Mission::empty    0x04
```

## 4. `FBOContainer::Release` veneer target (GOT-level fix, not counted)

`FBOContainer::Release` was already `byte == true` before this pass, because the
function's last instruction is `b.w 0x19b458` and the veneer body is identical in both
binaries.  The veneer's literal at `0x19b464` is `0xffec4bbc`; the ARM veneer computes
`0x19b468 - 0x13b444 = 0x60024`, which is the `glDeleteFramebuffers` PLT slot.  The
source was calling `glDeleteBuffers` there, so the GOT slot content was wrong even
though the function bytes matched.  It now calls `glDeleteFramebuffers`.  This does not
change `byte_exact`, but it is the original callee.

## 5. Remaining four: `MGame` PLT slots

The four remaining `pct == 100.0 && !byte` rows are all `MGame` functions whose only
difference is a PLT slot:

| function | callee | orig PLT | ours PLT | delta |
|---|---|---:|---:|---:|
| `MGame::successCheck` | `Mission::setType` | `0x66c24` | `0x66c18` | `-0xc` |
| `MGame::startJumpScene` | `PlayerEgo::setDockingState` | `0x66ca8` | `0x66c9c` | `-0xc` |
| `MGame::gameOverCheck` | `PlayerEgo::isInWormhole` | `0x66c84` | `0x66c60` | `-0x24` |
| `MGame::switchCamera` | `TargetFollowCamera::setRotationAroundTarget` | `0x66c0c` | `0x66c00` | `-0xc` |

The PLT order is the first-reference order.  Three symbols are inserted too late in
ours: `Standing::setStanding`, `PlayerEgo::autoTurretIsEnabled`, and
`PlayerEgo::setAutoTurret`.  Their first references are all inside the partial
`LevelScript::process` reconstruction, whose code layout differs from the original.
The original first-reference addresses (from `objdump -d`) are:

```
Standing::setStanding                 0x139b0e
TargetFollowCamera::setRotation...    0x139d94
Mission::setType                      0x13a04a
PlayerEgo::autoTurretIsEnabled        0x13a7fc
PlayerEgo::setAutoTurret              0x13a80c
PlayerEgo::isInWormhole               0x13c22e
PlayerEgo::setDockingState            0x13cd8e
```

Our reconstructed `LevelScript::process` has a different order, visible in the
relocation table of `o139_LevelScript.cpp.obj`:

```
TargetFollowCamera::setRotation...    +0x1eb2  (0x139bca)
PlayerEgo::isInWormhole               +0x3dfa  (0x13bb12)
Standing::setStanding                 +0x4042  (0x13bd5a)
PlayerEgo::autoTurretIsEnabled        +0x472c  (0x13c444)
PlayerEgo::setAutoTurret              +0x473e  (0x13c456)
PlayerEgo::setDockingState            +0x4cc2  (0x13c9da)
```

So the remaining four are a consequence of the incomplete `LevelScript::process`
body, not of `MGame`.  A full reconstruction of that function (or a source shape that
puts the three first references at the original offsets) is required.  This is a
hypothesis for the fix; the PLT-slot deltas themselves are measured.

A negative control: swapping the mission-5 and mission-50/51 branches in
`LevelScript.cpp` (semantically safe, because the mission ids are mutually exclusive)
moved `byte_exact` from 4492 to **2738** because it changed the whole function's block
layout and therefore many PLT slots.  It was reverted.
